## 1. 核心问题：数据流断裂（必须最先修）

```
理想链路（用户期望）:
  导入真实 Excel ──▶ 落库(教师/考场/班级/科目/考试) ──▶ 排考器读真实数据 ──▶ AI策略作为约束 ──▶ 真实排考结果 ──▶ 改派/发布/统计/导出

真实现状（断点 ✗）:
  导入真实 Excel ──✗只校验不落库──  (数据丢弃)
  排考器 ──✗──  永远读 ScheduleFixtureFactory.feasible() 写死样本（6教师/2考场/3考试）
  AI 策略 DSL ──✗──  解析后塞进 sessionStorage 即丢弃，从不进 OR-Tools
```

**关键证据（已确认 CONFIRMED）**：
- `scheduling/service/ScheduleJobService.java:128` → `prepareRunForTask(orgId, task, fixtureFactory.feasible())` 永远传写死 fixture
- `scheduling/solver/ScheduleFixtureFactory.java:36-55` → 硬编码 6 教师/2 考场/3 考试（王雅宁/李明远…、2026-06-08、数学/英语/物理）
- `importer/service/ImportValidationService.java:60-106` → 全 service 无任何 `Repository.save()`，导入永不写库；**后端根本没有 import-commit 端点**
- `ai/service/AiPolicyService.parse` 真解析 DSL 并落 `ai_call_log`，但 `CpSatScheduleSolver.solve(ScheduleFixture)` 签名**无 DSL 入参**，scheduling 包对 PolicyDsl 零引用 → DSL 被丢弃
- OR-Tools CP-SAT 求解器**本身是真的**（`CpSatScheduleSolver.java:33-167`），结果也真落 `schedule_assignment` 库 —— 只是吃错了输入

> **结论**：求解器、数据库 schema、各 CRUD 端点都是真的、好的。**缺的是把它们串起来的"真实数据流"那几根线**。这决定了 Epic 1 是一切的地基。

## 3. 缺口分类（决定修复策略）

| 类别 | 定义 | 修复成本 | 数量级 |
|---|---|---|---|
| **A. 前端未接线** | 后端端点已存在且真实，前端只 toast 没调 | **低**（建表单+接 api）| ~30 个动作 |
| **B. 后端数据流断裂** | 端点存在但逻辑是 stub/fixture，需补真实逻辑 | **高**（核心后端改造）| ~6 处（致命）|
| **C. 后端能力缺失** | 端点根本不存在，需新建 | **中** | ~8 个（改密/dashboard聚合/通知投递/学期覆盖等）|
| **D. 安全硬伤** | RBAC + 演示密码 | **中** | 2 处（必修）|

> **洞察**：成本最高、价值最高的是 **B 类（数据流）**，但它**解锁全盘**——修好后 Quick/AI/Edit/统计/详情 立刻从"描述 fixture"变成"描述用户真实数据"。**A 类**虽多但单点便宜、可并行、见效快。

## 4. 打通路线图（Epic 化，按优先级与依赖排序）

> 每个 Epic = 一份独立的、可单独交付可测试的子计划。优先级 P0 > P1 > P2 > P3。

### 🔴 Epic 1 — 真实数据流地基（P0，最高优先，解锁全盘）
**目标**：用户导入的真实 Excel → 落库 → 排考器真正基于它求解。
**范围**：
1. **导入落库（import-commit）**：新增后端逻辑，把校验通过的 Excel 行 upsert 进对应表
   - 教师/考场/班级/科目 → master data 表（org 级，按 code upsert）
   - 考试安排 → `exam`/`exam_room`/`exam_class`（绑定 taskId）
2. **排考器读真实数据**：`ScheduleFixtureFactory.fromTask(taskId, orgId)` 从 `ExamRepository/TeacherRepository/ClassroomRepository` 构建 `ScheduleFixture`，替换 `feasible()`
3. **改 `ScheduleJobService.startTaskRun`**：line 128 改为 `fromTask(...)`，并在数据不足时返回结构化"数据不完整"错误（而非默默解 fixture）
4. 保留 `feasible()` 仅供测试/demo 显式调用
**依赖**：无（schema 已就绪）。**这是其他 Epic 真实价值的前提。**
**验收**：导入 A 校 142 教师/8 考试 → 排考结果包含这 142 名教师、8 场考试；导入 B 校不同数据 → 结果不同；fixture 路径仅测试可触发。
**工作量**：L（后端 3-5 天）。**风险**：solver 约束需适配真实数据规模（H1-H7 约束、可行性）；需准备真实规模压测。

### 🔴 Epic 2 — 安全基线：RBAC + 演示密码守卫（P0，上线前必修）
**目标**：消除越权漏洞与生产后门。
**范围**：
1. **方法级 RBAC**：`@EnableMethodSecurity` + 给 `/api/v1/admin/**` 加 `@PreAuthorize("hasRole('SUPER_ADMIN')")`；给写操作(改派/发布/CRUD)加角色/权限校验；消费已加载的 authorities
2. **演示密码守卫**：把 V4/V9/V10 demo seed 迁移移到**仅 dev profile 的独立 flyway.locations**，或改环境变量注入；`application-private/saas.yml` 设 `ignoreMigrationPatterns`/独立 locations；生产强制首登改密
3. captcha-debug 生产强制关闭
**依赖**：无。**可与 Epic 1 并行。**
**验收**：普通 ADMIN curl 超管端点 → 403；private/saas 部署不含 admin/Super001!!! 弱密码；生产 captcha 不返回 debugAnswer。
**工作量**：M。**风险**：RBAC 加严后需回归全部既有 E2E（避免误伤合法调用）。

### 🟡 Epic 3 — 主数据管理前端接线（P1，见效快）
**目标**：教师/考场/班级/科目的增删改 + 真导入 + 模板下载 + 真筛选全部可用。
**范围**（后端多已就绪，主要是前端 + 少量后端）：
1. 新增/编辑表单（drawer/modal）→ 接 `POST/PUT /teachers|classrooms|classes|subjects`
2. 删除按钮 + 确认 → 接 `DELETE /...`
3. 批量导入弹窗接真实文件上传 → Epic 1 的 import-commit
4. 模板下载链接指向 `GET /import/templates/{kind}`
5. 筛选接服务端参数（或保留前端过滤但接全部选项）
**依赖**：导入落库依赖 Epic 1；CRUD 不依赖。
**验收**：新增一名教师 → 刷新仍在、DB 有行；导入 50 行 → 列表真增 50 行；删除 → DB 真删/软删。
**工作量**：M（前端为主）。

### 🟡 Epic 4 — AI 策略真正驱动排考（P1）
**目标**：勾选策略 + 自然语言 DSL 真正作为 OR-Tools 约束影响结果。
**范围**：
1. `CpSatScheduleSolver.solve` 增加 `PolicyConstraints` 入参
2. 6 预置策略 → 映射为求解器软/硬约束；3 数值输入受控并下传
3. NL → DSL 解析结果 → 转译为求解器约束（而非丢弃）
4. `ScheduleJobService` 读取 task 关联的 policy 注入求解
5. AI 总结建议改为真实 LLM（可选，或明确标注规则生成）
**依赖**：**强依赖 Epic 1**（求解器先要吃真实数据，才谈得上加约束）。
**验收**：勾"班主任最多监考 2 科" → 结果中班主任监考≤2；改数值 → 结果随之变；空策略 vs 严策略结果不同。
**工作量**：L。**风险**：约束冲突导致 infeasible，需可行性回退与人类可读的冲突解释。

### 🟡 Epic 5 — 设置页 + 超管创建类接线（P2）
**范围**：

**依赖**：改密/设置端点需新建（C 类）。
**验收**：改密后旧密码失效、新密码可登录；超管真能创建一个新租户/账号并在列表出现。
**工作量**：M-L。

### 🟡 Epic 6 — 仪表盘聚合 + 顶栏真实化（P2）
**范围**：
