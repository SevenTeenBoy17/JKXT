# JKXT 真实学校监考验收体系设计

**版本：** 1.0  
**日期：** 2026-08-30  
**目标系统：** JKXT V2.0 智能排监考平台  
**数据性质：** 全量合成数据，不包含真实教师、学生、联系方式或健康信息

## 1. 目标与成功定义

本设计建立一套可重复、可审计、可扩展的真实学校监考验收体系，用来回答三个问题：

1. 在小学、初中、高中和多校区的大中小规模场景中，系统是否能始终满足排监考硬约束。
2. 在公平优先、健康照顾、稳定优先、效率优先、班主任保护、学科回避和应急韧性等不同策略下，AI 是否能正确理解策略、保持硬约束不变，并产生可解释的差异化方案。
3. 在请假、生病、临时公务、年龄或行动照顾、职务冲突、学科/班级冲突、考场关闭和跨校区延误等扰动发生后，系统能否快速修复且尽量少改动原安排。

发布级成功必须同时满足：所有阻断级硬约束为零违规；预期可解用例达到规定成功率；预期无解用例被如实识别；AI 不静默弱化硬约束；公平、性能、稳定性和证据完整性达到分层门槛；无未关闭的 P0/P1 缺陷。

## 2. 范围

### 2.1 本轮交付范围

- 真实学校监考测试计划书与执行顺序。
- Agent 角色、责任边界、共享状态和审查分组。
- 固定随机种子的合成数据生成器。
- 小型、标准、大型、极限四个规模层的教师、考场、考试、扰动、AI 策略和运行矩阵。
- 与 JKXT 当前三类 Excel 导入表头兼容的投影文件。
- 机器可读场景、验收规则和证据契约。
- 数据完整性、可复现性和 Excel 可读性的静态验证。

### 2.2 不在本轮范围

- 不向当前 `jkxt_private` 业务库批量灌入数据。
- 不修改求解器、后端接口、前端或数据库结构。
- 不把地方惯例、年龄或健康状况自动视为全国统一强制规则；这些均以测试租户的显式策略配置为准。
- 不使用真实个人身份、联系方式、诊断或请假记录。

## 3. 方案选择

采用“可执行验收包”而不是纯文档或立即在线压测：先冻结数据、策略、预期结果和证据格式，再在隔离测试租户/数据库中执行。这样可以让每次测试使用同一输入和同一判定口径，也能把当前产品“不支持表达的现实属性”与“求解器违反约束”区分开。

## 4. 系统边界与数据流

```text
学校基线数据 -> 场景覆盖层 -> 策略/人格提示 -> JKXT 导入投影
      |               |                |              |
      +---------------+----------------+--------------+
                              |
                         隔离测试执行
                              |
        排班结果 + AI 解释 + 日志 + 性能 + 数据库真值
                              |
                   约束 Oracle / 统计 Agent
                              |
                       独立验收 Reviewer
```

富数据真值使用 JSONL，保存教师照顾、职务、班主任、任课班级、可用时段、跨校区时间、资格、备用状态等属性。JKXT 当前导入兼容层只投影现有表头：教师 `工号/姓名/性别/年级/任教学科/手机号/邮箱`，考场 `考场编号/考场名称/楼栋/楼层/容量/考试容量/考场类型/设施标签`，考试 `考试科目/年级/考试日期/开始时间/结束时间/考场编号/人数/监考人数`。无法被当前数据模型表达的属性必须被标为“能力缺口”，不得假装已被求解器验证。

## 5. 数据规模与组合

四个基线层分别用于功能、发布、规模和容量画像：

| 层级 | 学校原型 | 教师 | 考场 | 考试考场次 | 发布属性 |
|---|---|---:|---:|---:|---|
| S | 乡镇小校/单校区 | 64 | 18 | 56 | 必过 |
| M | 城区标准学校 | 240 | 72 | 480 | 必过 |
| L | 城市多校区学校 | 760 | 260 | 2,100 | 必过 |
| XL | 区域级极限画像 | 1,600 | 540 | 6,000 | 容量画像，不单独阻断发布 |

每个基线通过场景覆盖层产生正常、紧张、严重、预期无解四种压力；场景至少覆盖 20 个家庭。策略层至少包含 8 种策略。执行采用固定种子和配对运行，以免把一次幸运求解当成产品能力。

## 6. Agent 架构

测试执行采用分波次 Agent 团队：测试总监负责状态机；学校运营 Agent 生成现实事件；教师画像 Agent 维护照顾与冲突；考试资源 Agent 维护考试和考场；策略 Agent 生成并变异提示；独立约束 Oracle 计算预期；扰动 Agent 注入事件；执行 Agent 调用系统；统计 Agent 比较策略；证据 Agent 固化输入/输出哈希；独立 Reviewer 做最终判定。

生成者、执行者、Oracle 和 Reviewer 必须属于不同责任组。各 Agent 只写自己的租约目录，不能覆盖其他 Agent 的结果。Reviewer 只能读取不可变证据包，不能修补结果后再批准。

## 7. 约束分层

### 7.1 永不放宽的硬约束

- 所有需要监考的考场次 100% 覆盖，人数精确匹配。
- 教师同一时段不重复；考场同一时段不承载两场考试。
- 请假、生病、不可用或明确禁止时段的教师不被安排。
- 显式配置为硬规则的本学科、本班、班主任、资格、校区通勤和无障碍限制为零违规。
- 预期无解时返回无解/冲突解释，不伪造成功结果。
- AI 不得静默删除、弱化或反转硬规则。

### 7.2 可比较的软目标

- 工作量公平、连续场次、跨校区移动、年龄/健康照顾、班主任和管理职务保护。
- 扰动后的最小改动、备用教师消耗、鲁棒性余量。
- 不同策略下的目标排序与解释一致性。

软目标使用归一化指标比较，不能用某个群体的原始排班次数直接作跨学校结论。

## 8. 验收门槛

- P0 硬约束：零违规；任何一项非零即整批失败。
- 预期可解成功率：S/M 为 100%，L 至少 98%；失败必须区分 `infeasible`、`timeout`、`unknown`。
- 预期无解识别率：100%，并给出可定位的冲突类别。
- AI 明确提示解析准确率至少 98%；矛盾/不支持提示识别率 100%；不得静默降级。
- 公平性：正常场景教师任务 Gini 不高于 0.12，紧急场景不高于 0.18；同时报告最大值、极差、标准差和分位数。
- 单人临时缺勤修复：未受影响分配保留率至少 95%，新增硬违规为零；群体缺勤保留率至少 80%。
- 性能：S/M/L 的 p95 分别不超过 15/45/120 秒；XL 记录容量拐点，不掩盖超时。
- 可复现：同版本同种子的规范化 JSONL 与工作簿单元格内容摘要 100% 一致；每次 XLSX 容器自身的实际文件哈希仍单独记录，因为 OOXML 打包元数据可能变化。
- 证据：每个运行有输入清单、种子、策略版本、系统版本、结果哈希、指标、日志索引和 Oracle 判定；终态、Oracle、H01-H12 与阻断能力缺口必须跨字段一致；D1-D4 共享冻结 baseline 父标识，真实执行后共享同一 assignment snapshot 哈希；完整率 100%。
- 总分：所有阻断门通过后，质量加权分至少 90/100，且无未关闭 P0/P1。

上述数值是项目验收阈值，不是外部法规。正式执行前若学校存在更严格的书面制度，以更严格者覆盖并保留版本记录。

## 9. 风险与降级

- 当前数据模型不能表达的现实属性记录为产品能力缺口，不计为“排班通过”。
- 已有 K12 审计存在预期无解场景实际成功、负向数据硬违规和待完成 UAT；新体系必须把预期 Oracle 与系统结果分离。
- 大规模运行必须使用独立数据库、租户前缀和可恢复快照；当前运行中的演示环境只做健康检查，不做批量执行。
- 随机结果必须固定种子；策略比较使用相同输入配对，并报告 95% 自助法置信区间。
- 任何证据缺失、规则解释不一致或 Reviewer 非独立，终态只能是 `incomplete`。
