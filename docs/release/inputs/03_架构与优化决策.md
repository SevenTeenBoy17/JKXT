# JKXT｜架构与交付优化决策

## 一、优先补齐真实闭环，不再另造一套系统

当前项目已经有Spring Boot后端、数据库、会话、安全过滤器、多个排班/规划入口与通知模型。建议保持模块化单体，先以接口与数据不变量收口。微服务、Kubernetes和全量TypeScript迁移不是本轮先决条件；没有容量与维护收益证据不引入。

用户要求“后端功能均正常”，应落实为：所有已承诺交付的可见功能和可调用入口都有真实实现与验收；不是删掉做不出来的核心功能，也不是把缺配置服务隐藏后给全站打满分。可选外部能力需要单独确认交付范围。

## 二、以功能证据链组织代码，而不是仅按目录打勾

每项业务都追踪：页面事件、前端请求、实际控制器、权限、业务服务、事务和数据库、异步事件、最终输出及测试。对Spring运行时路由与OpenAPI交叉核对，再补充后台任务、脚本、流式订阅和下载。对不在OpenAPI的功能不能默认忽略。

成功标准示例：新增教师不仅返回201，还应产生正确org_id的记录；刷新/重启后存在；跨校读写被拒；无权限请求没有副作用；相关报表使用正确数据。错误对象不能只是一个“保存失败”，要区分校验、权限、版本冲突、依赖故障，并给用户可操作提示与trace。

现有配置、迁移和历史文档可能落后于真实代码。注释“已修复”、目录“安全中心”、文件名“Production”都不能代替实际执行。

## 三、新旧排班必须统一硬约束，但不要求不同引擎输出完全相同

旧 `ScheduleFixture.TeacherInput` 不承载主监资格字段；新 `DeterministicInvigilatorAllocator` 通过独立eligibility、资格要求和既有岗位映射处理。这个差异是已确认的代码事实，不等于已经证明所有旧入口都会排错。执行者需追踪入口是否作了充分预过滤和桥接，建立跨入口能力矩阵。

建议一份规范化输入快照承载学校、学期、输入版本、教师可用性、主副监资格、有效占用、考场容量和业务策略。快速排班、AI策略排班、手工调整及发布必须使用同一套业务约束定义。已发布历史数据不能被当前教师姓名/资格修改静默改写。

配置开关要区分“不可关闭的安全/业务底线”与“学校可选偏好”。班主任上限、回避、时长平衡等由业务范围定义硬/软，不因求解困难擅自降软。性别或年龄示例不是普遍强制规则，不能把原型文案当作规范依据。

### 最小反例：资源够用也可能被贪心顺序用错

早场08:00–09:00、晚场10:00–11:00，各需一名主监。A/B均有资格且每日最多一场。A两场可用；B晚场请假；A的编号排序靠前。有效安排是早场B、晚场A。

按当前已读分配器“按时间与岗位依次取当前负载最小者”的局部路径，可能先给早场A，再在晚场耗尽可用者。该结果不能证明问题本身无解。此处是静态推导的待复现风险，尚未在JKXT实际Java运行环境执行。

整改选项：先分配最受限制岗位并增加回溯/修复；或对监考分配使用完整CP-SAT/匹配求解，并保留整体时间预算。优先选有测试与容量依据的最小变更。未知或预算耗尽输出搜索未完成，不伪装INFEASIBLE。

### 独立验证结果

对小规模问题提供独立穷举/匹配对照；对产出提供独立硬约束检查。验证器不能只是把求解器内部同一个eligibility函数再调用一遍。不同算法可以输出不同但同样可行的安排；验证的是完整覆盖、约束与目标度量，不是逐人排列完全一致。

## 四、确定唯一生效版本和发布入口规则

当前有旧task/run与新plan/revision两个链路；新链路存在审批与严格发布检查，而旧发布实现门槛不同。建议逐步以一个领域发布服务/统一校验边界作为权威；旧API通过适配保留兼容，明确逐步退出条件，不直接删除破坏调用方。

发布必须针对当前输入和有效资格重校验。重复发布要幂等，旧版本冲突拒绝覆盖。已发布安排发生变更时使用受控后继版本或应急变更，保存差异、操作者、原因与通知对象。仪表盘、工作台、统计、下载、通知共同指向已定义的生效版本。

## 五、数据库：保护真实数据与可升级性

保留PostgreSQL约束、组织字段、唯一性和历史记录。核心跨表关系优先用数据库可表达的外键、唯一或排他约束兜底；跨行条件不要随意塞进只能可靠约束单行的CHECK。

重点复核V30复合外键 `(org_id, projected_run_id)` 的 `ON DELETE SET NULL`：PostgreSQL默认将该外键涉及的所有引用列置空，可能触发org_id非空约束；即便仅清run字段，还需要维护配对游标CHECK。具体采用受控拒绝、清游标的追加迁移或历史保留，由合法删除场景决定，不机械删除约束。

每次迁移都测试新装与旧版升级。已有迁移不直接改；不通过clean/repair删除历史校验问题。数据库测试必须使用独立PostgreSQL；测试配置已有身份保护，不以H2模拟代替PostgreSQL触发器、JSONB或锁语义验收。

## 六、会话与安全：保护既有正确机制，补齐寿命和协议

现有Cookie/Redis会话与权限过滤应保留并完善。优先处理用户会话索引与会话本体TTL不一致、绝对过期、账号状态/权限版本变化、强制改密服务端限制、跨学校和本人资源范围。

学校与平台入口隔离如采用WIP，应作为一个协议迁移：登录、me、退出、请求上下文、CSRF、SSE、下载、多标签页同批设计、分步验证。不能只复制新后端类而让旧前端继续发送旧请求。

CSRF采用成熟SPA支持机制并按目标Spring版本文档实现。会话Cookie仍HttpOnly；用于前端读取的CSRF载体与会话凭据分开。普通写请求、multipart上传和登出都覆盖，不能为图方便把全部业务路径豁免。

## 七、异步任务：数据库里有QUEUED并不等于任务可靠保存

进程内Executor只保存内存执行意图。为计算任务增加持久领取、租约/心跳、超时回收、取消与恢复语义；可优先复用已有数据库任务表和outbox，不必立即引入额外中间件。

按数据规模限制同时计算数、每校排队量和输入复杂度。整体deadline覆盖重试；区分排队与计算时间。请求线程不承担不受限的求解，取消不是只更新页面文案。失联任务恢复后不能把晚到结果覆盖用户已经修改或取消的版本。

## 八、通知与平台功能必须真实

`LoggingEmailSender`明确只记录日志并返回LOGGED；`NotificationDispatcher`已区分logged_only，不应把它说成完全假成功，也不能把enabled=true说成SMTP接入成功。

新通知service对非IN_APP通道返回CHANNEL_NOT_CONFIGURED，已有部分真实性保护。需要完善的是统一两套通知口径、实际消费调度、重试、本人阅读、确认/拒绝/签到与历史版本的关系。生产请求中的failDeliveryIds等测试用途参数应隔离；客户端提交的阅读receipt不能覆盖服务器提供方证据。

新增外部发送器时，以事务事件提交与消费者实际发送解耦。用批准的测试收件人和真实提供方消息ID验证，不把“提供方受理”升格成已读。2FA、IP封禁、自动备份、维护开关都必须验证实际使用方；仅保存配置不算实现。

## 九、备份与运行观测

备份脚本采用失败即终止、临时文件、非空检查、成功后改名与完成清单；服务端重算校验和，不把任意.sql登记为成功。恢复演练比哈希存在更重要。

应用仅按最小权限读取备份；使用独立备份身份、保留策略与异机副本。不要为备份便利给业务容器挂Docker socket。恢复流程在隔离库验证，并记录真实RPO/RTO。公网单校部署也需要这些底线。

健康探针区分进程存活、能否接受业务和可选AI故障。告警需实际送达测试；只有日志不算告警已接通。客户端来源IP必须按单层/双层代理各自配置，不盲用同一份反向代理配置。

## 十、前端整改与后端同步

首要的是业务输入输出与真实状态，不是重新美化。统一请求层处理权限、CSRF、必要的幂等键、版本游标、超时和trace。相同业务重试复用同一幂等键；用户改动意图才生成新键；写超时先查状态，不盲目再提交。

生产构建逐步替换浏览器Babel与React开发包；保留global/window桥接的兼容过程，审查现有babel-script-scope、脚本顺序、动态Tailwind类及缓存。先有路由和视觉回归，再拆大组件；不把一次性全量模块化作为先决条件。

原生EventSource构造参数仅提供URL和withCredentials等标准选项，不能像普通fetch一样注入自定义请求头。若会话隔离强制要求上下文头，需选择支持相同协议的流读取实现或受控Cookie/入口设计，并测试浏览器实际行为。不要把长期会话密钥塞进查询参数解决。

加载、空态、失败、权限不足、旧版本冲突、断网、重复点击、多标签页和下载都需要真实后端验证。截图用于视觉检查，不证明业务落库或通知成功。

## 十一、团队与Codex协同

一个集成负责人维护共享契约和迁移编号；身份安全、数据导入、算法发布、通知报表、前端可分别在独立分支/worktree处理。只有实际存在子代理时才并行；不能把角色名称列表当作真正独立审阅。

各阶段做到小提交、小回归、真实证据与可恢复进度。使用AGENTS.md保持约束，使用STATUS/DECISIONS/API-CATALOG记录状态；指令与计划不是测试结果。创建本地环境脚本时遵守沙盒和审批，不要求无限权限。

## 十二、放行只针对明确范围

84项场景是最低基线，不是所有端点或所有可能输入的替代。发现新入口补充场景；对从交付范围排除的功能取得明确认可。必需场景未执行、缺报告、关键跳过、仅mock真实依赖均不得生产放行。真正上线需人工批准和学校业务确认；代码审查不是法律、合规或素材授权认证。
